# Gamma prompt: RepoGuide AI judge presentation

Create a 9-slide, 16:9 hackathon presentation for **RepoGuide AI**. Audience: judges who have not seen the product. Goal: explain the problem, user journey, architecture, and exactly where Gemma 4 is used in 4–5 minutes. Use plain English, large labels, minimal text (maximum 35 words per slide), and clear visuals. Use the existing dark-purple and lavender product style. Add one short speaker note (20–30 seconds) per slide. Use simple arrows and diagrams, not decorative AI imagery. Leave space for real product screenshots; do not invent screenshots, metrics, user counts, accuracy claims, or deployment claims.

The product: RepoGuide AI turns a GitHub repository into an evidence-backed map of code structure and dependencies. It provides an architecture graph, impact analysis, search, history/hotspots, grounded Ask, PR review, and MCP access for IDE agents. The graph is built from code parsing and imports, **not generated by an LLM**.

Make these slides:

1. **Title:** RepoGuide AI — Understand any codebase faster. Visual: GitHub repository transforming into a readable graph. Subtitle: Architecture, impact, and evidence-backed answers.
2. **Problem:** A new developer faces unfamiliar files, hidden dependencies, and slow code reviews. Visual: tangled file tree becoming a clear map. Use three short pain points.
3. **Solution:** One repository index powers four outcomes: architecture graph, impact analysis, grounded Ask, and PR review. Visual: four labeled feature cards around one shared index.
4. **User workflow:** Paste a public GitHub URL → repository is cloned and indexed → inspect architecture/dependencies → ask a question with cited code → check impact or review a PR. Visual: five-step horizontal journey with simple icons. Note that GitHub sign-in is used for private repositories.
5. **How indexing works:** Git clone → Tree-sitter parses TypeScript, JavaScript, Python, and Go → module/symbol dependency edges → PostgreSQL + pgvector index → background search chunks and Git history. Visual: labeled pipeline with a sample import edge. Make clear that the graph comes from source code evidence.
6. **System architecture:** Browser/Next.js web and BFF → Fastify API → Redis job queue/worker → PostgreSQL + pgvector. Show GitHub feeding the indexer and Google AI Studio's hosted Gemma 4 endpoint connected only to the API's AI provider. Show MCP clients using the same indexed data. Use arrows labeled with their purpose; keep the diagram readable.
7. **Where Gemma 4 is used:** Spotlight on **Gemma 4 26B A4B IT** (`gemma-4-26b-a4b-it`) through Google's Gemini API. Two branches: (A) Ask: user question + retrieved code snippets/graph context → Gemma 4 → answer with file/line citations and confidence; (B) PR review: changed files/symbols + test signals → Gemma 4 → structured review findings. State that local embeddings power search and Tree-sitter builds the graph; Gemma 4 reasons over retrieved evidence. Do not call Gemma 4 “Gemini 3.8 Flash.”
8. **Demo story:** Show a realistic three-panel storyboard: paste a repository URL, open its architecture map, ask “What breaks if this module changes?” and inspect cited files. Reserve screenshot placeholders if real screenshots are supplied. Do not fabricate analysis results.
9. **Close:** RepoGuide AI helps developers move from unfamiliar repository to informed change. Visual: a clean code graph with the path “Explore → Ask → Review.” End with a large “Live demo” cue and a placeholder for the actual app URL or QR code.

For every diagram, use high-contrast labels and arrows. Add concise speaker notes that explain what the judge should notice. Keep technology names accurate. Use no more than one technical diagram per slide. If a screenshot or live URL is not provided, use a clearly labeled placeholder rather than inventing one.
